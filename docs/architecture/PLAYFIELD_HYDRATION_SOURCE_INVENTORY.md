## Current composition path

Normal playfield creation is lazy and instance-owned:

```text
ZoneClient.CreateCharacter
  -> ZoneServer.PlayfieldById
  -> RuntimeOwnershipRegistry.GetOrCreate
  -> ZoneServer.CreateOwnedPlayfield
  -> new Playfield
  -> PlayfieldRuntimeSystems
  -> resolve/register statels
  -> PlayfieldObjectMaterializationRuntimeService
```

`RuntimeOwnershipRegistry` serializes creation and invokes its factory once for a new playfield key. `ReplacePlayfieldRuntime` disposes the complete old instance before invoking the same factory for a replacement.

The current constructor mixes definition reads and runtime effects. Its effective startup order is fixed by `PlayfieldObjectMaterializationRuntimeService.MaterializeStartupObjects`:

1. Read and immediately instantiate database mob spawns, except rows explicitly suppressed by content-module compatibility policy.
2. Register the first matching hardcoded/capture-backed content modules, which immediately create NPCs, encounters, vendors, services, and schedules.
3. Join RDB vending-machine statels to DAO vendor rows and immediately create vendors.
4. Read DAO static dynels, append the narrowly scoped capture-backed missing-prop overlay, and immediately create/register static dynels.
5. Refresh the runtime dynel registry from the global pool.

That call order is current precedence. It is not a clean merge of static definitions.

## Implicit precedence and duplicate ownership

The following rules are authoritative because of current call or branch order, not because a declarative merge policy exists:

- `playfields.dat` is loaded, then DAO teleport rows patch its function arguments, then PF127 hardcoded compatibility can replace the resolved destination and append reverse-exit/collision events.
- `PlayfieldContentDataProvider.ResolveStatels` checks `PFData` first. Only a missing row can select the empty-statel exceptions for private cities, mission instances, PF7001, or luxury apartments; every other missing id throws through the final dictionary indexer.
- DB mobs are instantiated before content registration. A module suppression decision must occur before instantiation; no later deduplication exists.
- Content modules execute in the constructor order in `PlayfieldRuntimeSystems`. Their `Register` methods call one shared side-effect fan-out whose child spawn calls have their own PF guards.
- Vendor statels come from the already patched extracted playfield data. DAO vendor linkage overrides only hash/template identity; the statel keeps placement. Missing DAO linkage falls back to an empty vendor from the statel template.
- DAO static dynels are yielded first. Capture-backed Arete missing props are appended afterward and only if their identity is absent from the adapted DAO list.
- Generated/accepted ordinary population, named encounters, vendors, quests, and service NPCs have separate owners. A shared AO identity or location does not imply one source supersedes another.
- PF655 has explicit dual module recognition: Montroyal is a compatibility skeleton and Andromeda owns captured NPC registration. Arete deliberately excludes PF655 to prevent a second registration.

Known duplicate or collision surfaces are DB mobs versus capture-owned spawns, `Playfields.xml` versus `playfields.dat` metadata, RDB vendor statels versus DAO vendor/template rows, DAO static dynels versus capture missing props, physical NPC placement versus JSON quest/dialogue ownership, and geometry structure versus captured live state.

## Central seam and Stage 1 constraint

The narrow stable composition seam is `ZoneServer.CreateOwnedPlayfield`, the single factory supplied to `RuntimeOwnershipRegistry<int, IPlayfield>`. Stage 1 may wrap this factory in a Legacy-only coordinator without changing the `Playfield` constructor or the order inside `PlayfieldObjectMaterializationRuntimeService`.

It is not safe in Stage 1 to make the current `Playfield` constructor produce a hydrated definition: the constructor creates buses, registries, timers, NPCs, vendors, statels, static dynels, schedules, scripts, and global-pool entries while reading sources. A side-effect-free DAO hydrator therefore remains a Stage 2 prerequisite, not an implementation in this tranche.
